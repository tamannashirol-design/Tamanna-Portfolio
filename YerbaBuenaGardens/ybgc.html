01 · Overview

The Gardens sit next to the Metreon, and most Gen Z visitors don't know they exist.

Yerba Buena Gardens sits in the middle of SoMa, next to Metreon and a cluster of museums, and the age group it needs most has no reason to know it exists. There's no social proof and poor presence on TikTok, the channel Gen Z actually uses to find things to do in SF.

So I designed a companion app that makes the Gardens discoverable and worth coming back to.

I interviewed the staff and the visitors they want to reach, built a working MVP in Lovable and Cursor, tested it twice, and fixed what each round found. YBG's IT team is taking it to launch.

03 · Core Features

Four features, each tied to an interview finding.

01

Creator Feed

A TikTok-style feed of visitor and creator content, so discovery happens in a format Gen Z already trusts.

Vertical endless scroll: the lowest-friction way to keep watching.

02

RSVP

Event RSVPs that show who's going, lowering the social risk of showing up alone, which came up repeatedly in interviews.

03

Map + Badges

A consolidated map of hidden gems and amenities, with badges earned by exploring and redeemable for real rewards like free bowling.

Badges unlock as you explore, not through a fixed points system, so there’s a reason to come back.

04

Nudges

SMS and push notifications in a Gen-Z voice, turning a one-time visit into a repeat habit.

In testing, event notifications were one of the top reasons participants said they’d reopen the app.

04 · Iterations

What round-one testing
forced me to fix.

Moderated usability testing with 5 participants on the first prototype surfaced four issues before the design reached a high-fidelity build.

Finding 01

The badge flow had poor hierarchy or labels. Users couldn't tell which badge to collect, how to earn one, or how badges connected to the map.

Solution

Added color and micro-animations to make progress and next steps legible, and tied badge-earning to the map so the two flows connected.

Finding 02

The option to post a video to the creator feed wasn't clear. Users didn't realize they could contribute content, only consume it.

Solution

Added a fixed feature CTA to the feed and added an occasional get featured ad while scrolling, the ad frequency changes.

Finding 03

An accessibility list-view was added for the map, but in testing it felt confusing due to many buttons and it competed with the main map view instead of supporting it.

Solution

Replaced the two competing buttons with a single Map/List toggle, so the accessible list supports the map instead of competing with it. The list view still needs its own usability pass.

Also fixed: the events icon and calendar view looked too alike, so I differentiated the icon set.

These fixes went into the high-fidelity build tested in round two. The badge flow was still the weakest task there, so I redesigned it again afterward (see Results).

“
Why This Matters

Figma prototypes fake state. Code has to remember it. Building in Lovable and Cursor meant the app had to work like real software, and small bugs that survived two rounds of testing showed up as soon as I could actually use it.

Figma file, local styles & auto layout

Handing a file to Lovable and Cursor is unforgiving: nothing carries over automatically. So I built proper text and color styles and auto layout across every screen, so engineering could build from it as a system.

Working With AI, Not Around It

AI helped me build faster, but the design decisions were still mine. Working within tight token limits in Cursor and Lovable made that clear.

Challenge

Lovable's credits ran out, even after 100 more were added. One Stripe prompt used up Cursor's.

Action

Split each feature into small prompts, tightened with Claude to name the function, the check, and the test case.

Result

All four features built, plus the badge redo after round two. Working MVP handed off.

Example: making paid-event RSVPs check the card
My first draft

The Stripe payment form currently lets any card number go through (even declined test cards like 4000 0000 0000 0002). The submit button is skipping the payment validation. Please update the RSVP button's submit handler to actually await the Stripe payment confirmation (stripe.confirmPayment or stripe.createPaymentMethod). It must throw a visible error on the screen if the card fails or is declined, and only complete the RSVP if Stripe returns a success status.

Tightened with Claude · 1.9 credits

The Stripe payment form lets any card through, including declined test cards (4000 0000 0000 0002). The RSVP submit handler is likely calling recordRsvp() without properly awaiting and checking the result of stripe.confirmPayment(). Please fix the submit handler so it:
1. Calls stripe.confirmPayment() with redirect: 'if_required'
2. Awaits the result and checks for an error object. If present, display the error message (e.g. error.message) visibly on screen and stop
3. Only proceeds to call recordRsvp() if paymentIntent.status === 'succeeded'
4. Does not silently swallow or ignore any Stripe error response
Test with decline code 4000 0000 0000 0002 to confirm it now blocks the RSVP and shows a visible error.

Most of my Lovable prompts cost 3 to 5 credits. This one cost 1.9.

By hand: I caught the bug by testing with Stripe's test cards, wrote the fix prompt from it, and re-tested. The approved card now completes the RSVP; others decline with an error.

07 · Reflection

What this taught me.

01

Small prompts beat one big one

Describing the whole app at once burned tokens fast. I only got usable results once I broke each feature into small prompts in a fixed sequence. It also made me define each screen's behavior before building it, which is the same discipline a handoff needs.

02

The MVP was for testing, not launch

I built it to show the idea works and to test it with real people. Making it secure and public is the IT team’s job, and knowing where my part ends is part of the work.

03

My biggest design decision wasn't the strongest lever

Badges got the most design effort and were the hardest feature to use in testing. When I asked what would bring people back, events beat rewards. Next time I’ll test the core idea earlier, not just how usable it is.
